01为什么要开这门课

第一性原理

语言模型是什么？一个在 token 序列上的概率分布。按链式法则分解：p(x₁…xₙ) = ∏ p(xᵢ | x<ᵢ)，于是“建模语言”就变成“给定前文预测下一个 token”，训练目标就是最小化负对数似然（交叉熵）。

约束是什么？三种稀缺资源：计算（FLOPs）、内存与带宽（字节）、数据（token）。这门课的所有内容都是一个优化问题：在这三种约束下，把模型效果做到最好。

分词为什么重要？模型的计算量随序列长度增长（注意力是平方增长），而词表大小决定 embedding 和输出 softmax 的规模，也决定每个 token 平均能见到多少训练样本。切得越细，序列越长；切得越粗，词表越大越稀疏。分词就是在这两者之间折中，BPE 用数据统计来做这个折中。

这是 CS336 的第三次开课（前两次是 2024、2025 春季）。和去年相比，“从零构建”的理念不变，内容上更注重单位时间收益高的概念（不要只见树木不见森林），并加入了更多现代 LM 的组成部分：混合专家（MoE）、长上下文、智能体（agents）。

问题：研究者正在和底层技术“脱节”

  • 2016 年：研究者自己实现、自己训练模型。
  • 2018 年：研究者下载预训练模型（如 BERT）再做微调。
  • 今天：研究者调用 API 给闭源模型（GPT / Claude / Gemini）写 prompt。

抽象层级上升确实提高了生产力。但和编程语言、操作系统这类成熟抽象不同，LLM 的抽象是“漏”的：模型行为会受到分词、数据、训练细节的影响，调用者不理解下层就很难解释上层的现象。而且很多基础研究本来就需要把整个技术栈拆开来改。

课程理念要做基础研究，就需要完整理解这门技术。本课的方法是通过亲手构建来理解（understanding via building）。

但有个现实问题：语言模型已经“工业化”

  • 2023 年，GPT-4 据称训练花费约 1 亿美元。
  • 2025 年，xAI 为训练 Grok 搭建了 23 万张 GPU 的集群。
  • 前沿模型的构建细节不公开。GPT-4 技术报告明确写了：出于竞争和安全考虑，不披露架构、模型大小、硬件、训练计算量、数据集构建和训练方法。

我们没法训练前沿模型，只能做小模型（<1B 参数）。问题是，小模型不一定能代表大模型。讲义给了两个例子：

  1. FLOPs 在注意力和 MLP 之间的占比随规模变化。小模型里注意力占比较大，模型变大后，MLP 的计算量占绝对主导。所以在小模型上优化注意力得到的结论，到大模型上可能不再重要。
  2. 涌现能力（emergence）。某些任务的准确率在规模较小时接近随机，过了某个计算量阈值后突然上升（Wei et al., 2022）。只看小模型，你根本观察不到这些能力。

那这门课学到的东西，有哪些能迁移到前沿模型？

知识类型含义能否迁移
Mechanics（机制）东西是怎么工作的：Transformer 是什么、模型并行怎么做能教，能迁移
Mindset（思维方式）把硬件性能榨干、认真对待规模化（scaling）能教，能迁移
Intuitions（直觉）哪些数据和建模决策能带来好效果只能部分教，不一定跨规模迁移

关于“直觉”，讲义举了 Noam Shazeer 提出 SwiGLU 的论文（GLU Variants Improve Transformer, 2020）。论文结尾坦白说：这些结构为什么有效，他们无法解释，只能“归功于神的仁慈（divine benevolence）”。很多设计决策目前就是实验结果，没有理论依据。

苦涩的教训（The Bitter Lesson）的正确解读

  • 错误解读：只有规模重要，算法不重要。
  • 正确解读：能够随规模扩展的算法才重要。
accuracy = efficiency × resources模型效果 = 效率 × 资源

规模越大，效率越重要，因为浪费不起。Hernandez & Brown (2020) 的研究显示，2012 到 2019 年间，ImageNet 上达到同等精度所需的计算量因算法进步降低了 44 倍。

整门课的框架给定计算量和数据预算，能训练出的最好模型是什么？换句话说：最大化效率。

5.1 Basics：训练一个基础语言模型

分词（Tokenization）

模型操作的“原子”是什么？形式上，tokenizer 在原始输入（字节）和整数序列（token）之间相互转换。最常用的是 BPE（Byte-Pair Encoding），直觉是把输入切成频繁出现的片段。从效率角度看，它的好处是：

  • 缩短上下文长度：约 1000 字节 → 约 250 个 token。
  • 自适应计算：把更多建模能力分配给输入中“有意思”的部分。

理想状态是不需要 tokenizer、直接处理字节的架构（ByT5、MEGABYTE、BLT、T-FREE、H-Net）。它们很有前景，但还没有扩展到前沿规模。

模型架构

起点是原始 Transformer（2017），之后的主要改进：

组件演进方向
激活函数ReLU → SwiGLU
位置编码正弦位置编码 → RoPE
归一化LayerNorm → RMSNorm；QK norm；pre-norm vs post-norm
注意力全注意力、稀疏/局部注意力、GQA、MLA
循环 / 线性注意力Mamba、Gated DeltaNet 等状态空间模型
MLP稠密 → 混合专家（MoE）
形状隐藏维度、深度、头数、专家数

训练

  • 损失函数：例如多 token 预测（MTP，DeepSeek-V3 使用）
  • 优化器：AdamW、SOAP、Muon
  • 初始化尺度：Xavier、muP
  • 学习率调度：cosine、WSD（warmup-stable-decay）
  • 正则化：dropout、weight decay
  • 批大小：临界批大小（critical batch size）
  • MoE 专属：负载均衡（如 DeepSeek 的 aux-loss-free 方法）

5.2 Systems：把硬件榨干

资源核算

讲义里的例子：用 1T token 训练一个 70B 参数的模型，总计算量为

6 × 70×10⁹ × 10¹² = 4.2×10²³ FLOPs
补充：6ND 从哪里来

训练计算量约为 C ≈ 6ND（N 为参数量，D 为 token 数）。每个 token 在前向传播中，每个参数大约参与 1 次乘法和 1 次加法，即 2N FLOPs；反向传播要同时算对激活和对权重的梯度，约为前向的 2 倍，即 4N。合计 6N 每 token。下一课会详细推导。

模型参数要从显存（HBM）搬到计算单元（SM）。以 B200 为例：bf16 算力约 2.25 PFLOP/s，显存带宽约 8 TB/s。

  • Roofline 分析：判断计算是受算力限制（compute-bound）还是受显存带宽限制（memory-bound）。
  • 基准测试和性能剖析（如 nsight）：看实际运行情况。
补充推导

2.25×10¹⁵ ÷ 8×10¹² ≈ 281 FLOPs/字节。一个操作每读 1 字节数据，要做约 281 次以上浮点运算，才能让 B200 的算力跑满；低于这个“算术强度”，瓶颈就在显存带宽。逐元素操作（加法、激活函数）的算术强度远低于此，所以它们几乎都是 memory-bound。

Kernel

  • Kernel 是在 GPU 上运行的函数。用 PyTorch 时，每个基本操作都会启动一个标准 kernel。
  • 核心原则：组织计算，最小化数据搬运。
  • 未融合：读 HBM → 算 A → 写 HBM → 读 HBM → 算 B → 写 HBM
  • 融合后：读 HBM → 算 A 和 B → 写 HBM
  • 策略：算子融合（matmul + 激活）、分块（tiling，FlashAttention 的核心）
  • 需要理解的概念：warp divergence、内存合并访问（coalescing）、bank conflict、occupancy、异步批量内存传输
  • 工具：CUDA / Triton / CUTLASS / ThunderKittens

并行

  • 如果有 1024 张 GPU？GPU 之间的数据传输更慢，但“最小化数据搬运”的原则不变。
  • 使用经典集合通信操作：gather、reduce、all-reduce。
  • 把参数、激活、梯度、优化器状态切分（shard）到多张 GPU 上。
  • 切分计算的方式：数据并行、张量并行、流水线并行、序列并行、专家并行。

推理

推理不只是用来“用模型”，强化学习、测试时计算（test-time compute）、评测都需要推理。推理分两个阶段：

阶段做什么瓶颈
Prefillprompt 的所有 token 已知，可以一次并行处理（和训练类似）compute-bound
Decode一次只能生成一个 tokenmemory-bound
补充：为什么 decode 是 memory-bound

每生成一个 token，都要把全部权重从 HBM 读一遍，但只对很少的 token 做计算。以 70B 模型、bf16（约 140 GB 权重）、batch=1 为例：140 GB ÷ 8 TB/s ≈ 17.5 ms/token，也就是单卡理论上限约 57 token/s，而此时算力几乎闲置。增大 batch 能让多个请求分摊同一次权重读取，这就是 continuous batching 的意义。

加速 decode 的方法：

  • 用更便宜的模型：剪枝、量化、蒸馏。
  • 投机解码（speculative decoding）：用便宜的“草稿”模型先生成多个 token，再用完整模型并行打分。结果和完整模型的解码完全一致。
  • 系统优化：融合 kernel、continuous batching。

5.3 Scaling laws：用小实验预测大模型

假设你有 10²⁵ FLOPs 的计算预算，该用什么超参数？在目标规模上直接调参太贵了。

关键的概念转变不要只考虑单一规模，要设计一个scaling recipe：一个从 FLOPs 映射到超参数的“配方”。
  1. 在较小规模（例如最多 10²⁴ FLOPs）上跑实验，得到各规模下的 loss。
  2. 拟合 scaling law，预测该配方在目标规模（例如 10²⁵ FLOPs）下的 loss。

这样你就可以：用小规模实验优化面向大规模的配方；在真正训练之前预测最终 loss。scaling law 不会自动出现，需要精心设计配方，例如用 muP 等参数化方式实现超参数迁移。讲义强调：可预测性至少和最优性一样重要。

模型大一点，还是数据多一点？

给定预算 C = 6ND，是用更大的模型（N），还是训练更多 token（D）？Kaplan (2020) 和 Chinchilla (2022) 的做法：

  • IsoFLOP 曲线：对多个小的 FLOPs 预算，分别找出使 loss 最小的 N。
  • 对这些最优点拟合 scaling law，外推到大预算。
D ≈ 20 NChinchilla 经验法则：70B 模型大约应训练 1.4T token

注意：这条法则没考虑推理成本。实际部署时更想要小模型，所以现在的模型通常会用远多于 20N 的 token 来训练（“过度训练”）。

讲义还展示了 Marin 项目的实时例子：先用小规模实验预先登记（preregister）目标 loss，再训练大模型检验预测是否准确。

5.4 Data：模型该具备什么能力？

多语言？擅长对话？能做智能体编程？能力由数据决定。

评测

  1. 对内：指导模型开发。重要的是跨规模的平滑性和相对表现。
  2. 对外：衡量真实使用场景的绝对质量。重要的是生态效度（是否贴近真实使用）。

例子：困惑度（最好用不在互联网上的私有文档，避免数据污染）；高级任务评测如 GPQA、HLE、SWE-Bench、Terminal-Bench。LM 是通用的，所以需要多样的评测集。

数据来源与处理

数据不会从天上掉下来。来源包括爬取的网页、书籍、arXiv 论文、GitHub 代码等。版权数据能否以“合理使用”为由训练仍有争议，有时需要购买授权（如 Google 与 Reddit 的数据协议）。原始数据是 HTML、PDF、目录结构，不是纯文本，需要处理：

步骤内容
转换把 HTML/PDF 转成文本，提取正文
过滤用分类器保留高质量数据，去除有害内容
去重节省算力、避免记忆；用 Bloom filter 或 MinHash
配比每个来源该加权还是降权（RegMix、OLMix）
改写 / 合成用 LM 改写真实数据，使其更接近下游任务（WRAP）

数据类型：预训练数据（量大、多样）→ 中期训练数据（高质量，含长上下文）→ 后训练数据（SFT：对话、带工具调用的智能体轨迹）。

5.5 Alignment：从弱监督中继续提升

到这里，模型是用完全监督（预测下一个 token）训练的。模型已经不错之后，可以用弱监督进一步改进。为什么用弱监督？因为很多时候评判比生成容易。

基本模板：

  1. 让模型生成回答。
  2. 用人类、验证器（verifier）或 LM 评审给回答打分。
  3. 更新模型，让它偏向更好的回答。
算法要点
PPO来自强化学习，InstructGPT 使用
DPO针对偏好数据，更简单，不需要显式奖励模型和 RL 循环
GRPO去掉价值函数（value function），用同组采样的相对得分估计优势

挑战：RL 算法不稳定、难调；规模化需要大量新基础设施（异步 rollout 的推理）；需要不断在系统效率和 on-policy 程度之间权衡。

06贯穿全课的主线：效率

资源 = 数据 + 硬件（算力、显存、通信带宽）。问题始终是：给定固定资源，怎样训练出最好的模型？

今天我们受算力约束，所以各模块的设计决策都在榨干硬件：

07Tokenization 详解

这一单元受 Andrej Karpathy 的分词视频启发，推荐一起看。

7.1 Tokenizer 的接口与压缩率

原始文本通常是 Unicode 字符串，比如 "Hello, 🌍! 你好!"。语言模型在 token 序列（整数索引）上定义概率分布。所以需要两个过程：

  • encode：字符串 → token 序列
  • decode：token 序列 → 字符串
class Tokenizer(ABC):
    """Tokenizer 的抽象接口"""
    def encode(self, string: str) -> list[int]: ...
    def decode(self, indices: list[int]) -> str: ...

一个基本要求是往返一致（round-trip）：decode(encode(s)) == s。

衡量标准：压缩率

compression ratio = UTF-8 字节数 ÷ token 数

压缩率越高，序列越短。这很重要，因为注意力的计算量随序列长度平方增长。提高压缩率的办法是增大词表，但词表太大会带来稀疏性：很多 token 很少出现，模型学不好它们的 embedding。

观察真实 tokenizer

可以在 tiktokenizer 上体验。几点观察：

  • 单词和它前面的空格属于同一个 token，例如 " world"。
  • 同一个词在句首和句中的表示不同，例如 "hello hello" 中两个 hello 对应不同 token。
  • 数字会被切成每几位一段。

讲义用 GPT-5 的 tokenizer（tiktoken 的 o200k_base）编码 "Hello, 🌍! 你好!"：

Hello13225 ,11 ␣🌍 (前半)130321 🌍 (后半)235 !0 ␣220 你好177519 !0

20 个字节变成 8 个 token，压缩率 2.5；词表大小 200,019。注意 🌍 被拆成了两个 token：一个 token 对应的字节序列不一定是完整的 UTF-8 字符。

7.2 方案一：字符级 tokenizer

每个 Unicode 字符对应一个码点（code point），用 ord / chr 相互转换：ord("a") == 97，ord("🌍") == 127757。

class CharacterTokenizer(Tokenizer):
    def encode(self, string): return list(map(ord, string))
    def decode(self, indices): return "".join(map(chr, indices))

示例字符串编码为 13 个 token：[72, 101, 108, 108, 111, 44, 32, 127757, 33, 32, 20320, 22909, 33]。

  • 问题 1：词表非常大。Unicode 约有 15 万个字符，仅这个例子就要求词表至少 127,758。
  • 问题 2：很多字符很罕见（比如 🌍），浪费词表空间。
  • 压缩率只有 20 ÷ 13 ≈ 1.54。

结论：词表大、压缩率低，两头不讨好。

7.3 方案二：字节级 tokenizer

先用 UTF-8 把字符串编码成字节序列，每个字节是 0–255 的整数。ASCII 字符占 1 字节，其他字符占多个字节：

字符UTF-8 字节字节数
a611
你E4 BD A03
🌍F0 9F 8C 8D4
 
class ByteTokenizer(Tokenizer):
    def encode(self, string): return list(string.encode("utf-8"))
    def decode(self, indices): return bytes(indices).decode("utf-8")
  • 优点：词表只有 256，小巧，而且不会有未登录字符。
  • 缺点：压缩率恰好是 1，序列太长。Transformer 的上下文长度有限（注意力是平方复杂度），这不可接受。

7.4 方案三：词级 tokenizer

这更接近传统 NLP 的做法：用正则把字符串切成词。

regex.findall(r"\w+|.", "I'll say supercalifragilisticexpialidocious!")
# ['I', "'", 'll', ' ', 'say', ' ', 'supercalifragilisticexpialidocious', '!']

然后把每个不同的片段映射成一个整数。这个例子 44 字节 → 8 个 token，压缩率 5.5。

  • 优点：每个 token 都有意义（词是人发明的单位），压缩率高。
  • 缺点 1：词表大小等于训练数据中不同片段的数量，可能极大。
  • 缺点 2：很多词很罕见，模型学不到什么。
  • 缺点 3：词表大小不固定。
  • 缺点 4：训练时没见过的新词只能映射到特殊的 UNK token，既难看，又会搞乱困惑度的计算。

三种朴素方案对比

方案词表大小压缩率主要问题
字符级~150K1.54词表大且稀疏，压缩率低
字节级2561.00序列太长
词级不固定，巨大5.5*罕见词、UNK、词表不封闭
GPT-5 BPE200,0192.5需要训练

* 词级的压缩率来自另一个英文例句，不能和其他行直接比较。其余三行都是 "Hello, 🌍! 你好!"。

7.5 方案四：BPE（Byte Pair Encoding）

历史：BPE 由 Philip Gage 在 1994 年提出，本来是一种数据压缩算法。Sennrich et al. (2016) 把它用于神经机器翻译（之前的论文都用词级分词），后来 GPT-2 也采用了 BPE。

核心思想

在原始文本上训练 tokenizer，得到适合这份数据的词表。常见的字节序列用一个 token 表示，罕见的字节序列用多个 token 表示。

做法：从“每个字节是一个 token”开始，反复合并最常见的相邻 token 对。

BPE 同时解决了前面的问题：以字节为基础，不存在 UNK；词表大小由合并次数控制，是固定的；常见片段合并成长 token，压缩率高。

训练代码

def train_bpe(string: str, num_merges: int) -> BPETokenizerParams:
    indices = list(map(int, string.encode("utf-8")))
    merges = {}                                   # (index1, index2) -> 新 index
    vocab = {x: bytes([x]) for x in range(256)}  # index -> bytes

    for i in range(num_merges):
        counts = count_adjacent_pairs(indices)     # 统计每个相邻 pair 出现次数
        pair = max(counts, key=counts.get)         # 找最常见的 pair
        new_index = 256 + i
        merges[pair] = new_index
        vocab[new_index] = vocab[pair[0]] + vocab[pair[1]]
        indices = merge(indices, pair, new_index)  # 把所有该 pair 替换成新 token
    return BPETokenizerParams(vocab=vocab, merges=merges)

def merge(indices, pair, new_index):
    new_indices, i = [], 0
    while i < len(indices):
        if i + 1 < len(indices) and (indices[i], indices[i+1]) == pair:
            new_indices.append(new_index); i += 2
        else:
            new_indices.append(indices[i]); i += 1
    return new_indices

逐步演示：在 "the cat in the hat" 上合并 3 次

初始18 个字节 = 18 个 token
第 1 次合并(116, 104) 即 "t"+"h" → 256 = "th"出现 2 次
第 2 次合并(256, 101) 即 "th"+"e" → 257 = "the"出现 2 次
第 3 次合并(257, 32) 即 "the"+" " → 258 = "the "出现 2 次

最终 18 字节 → 12 个 token，压缩率 1.5。

注意平局

第 1 步时 ("t","h")、("h","e")、("e"," ")、("a","t") 都出现 2 次。讲义代码用 Python 的 max，平局时选最先出现的 pair。作业 1 对平局规则有明确要求，实现时以作业 PDF 为准，否则结果会和测试对不上。

用训练好的 tokenizer 编码新文本

def encode(self, string):
    indices = list(map(int, string.encode("utf-8")))
    for pair, new_index in self.params.merges.items():  # 按训练时的顺序依次应用合并
        indices = merge(indices, pair, new_index)
    return indices

def decode(self, indices):
    return b"".join(self.params.vocab[i] for i in indices).decode("utf-8")

用上面 3 条合并规则编码 "the quick brown fox"，只有开头的 "the " 被合并：

19 字节 → 16 个 token。合并规则只学自一句话，所以对新文本帮助有限。真实 tokenizer 在海量语料上学几万到几十万条规则。

为什么必须按顺序应用合并

后面的规则依赖前面产生的 token：257 = (256, "e") 要求 256（"th"）已经存在。如果顺序颠倒，(256, 101) 这个 pair 根本不会出现。

作业 1 要在此基础上做什么

  • 加速 encode：讲义里的 encode 会遍历全部合并规则，非常慢。只处理真正相关的合并。
  • 特殊 token：识别并保留 <|endoftext|> 这类特殊 token，不能把它拆开。
  • 预分词（pre-tokenization）：先用 GPT-2 的正则把文本切成片段，BPE 只在片段内部合并。
  • 让实现尽可能快。
补充：预分词为什么有用

GPT-2 的预分词正则：

'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+

它把文本切成“可选空格 + 字母串”“可选空格 + 数字串”“标点”“空白”等片段，这正是前面观察到“单词和前面的空格属于同一个 token”的原因。好处有两个：一是防止跨词合并，避免 dog.、dog!、dog? 各占一个词表项；二是提速，训练时只需统计每个片段的出现次数，再按次数加权统计 pair，不用每次扫描整个语料。

09自测题

先自己想，再点开看答案。

Q1为什么说字符级 tokenizer “两头不讨好”？

词表很大（Unicode 约 15 万字符），其中大量字符极少出现，embedding 学不好；同时压缩率很低（每个字符一个 token，英文约 1 字节/token），序列很长。词表大和序列长这两个缺点它都占了。

Q2用 6ND 估算：训练 8B 参数模型、15T token，需要多少 FLOPs？

6 × 8×10⁹ × 15×10¹² = 7.2×10²³ FLOPs。

Q3按 Chinchilla 法则（D = 20N），10²³ FLOPs 预算下最优的 N 和 D 大约是多少？

C = 6ND = 6N × 20N = 120N²，所以 N = √(10²³ / 120) ≈ 2.9×10¹⁰（约 29B 参数），D = 20N ≈ 5.8×10¹¹（约 577B token）。

Q4为什么 prefill 是 compute-bound，decode 是 memory-bound？

Prefill 时所有 prompt token 已知，一次读取权重就能对大量 token 做矩阵乘法，算术强度高。Decode 每步只生成一个 token，却要把全部权重（和 KV cache）从 HBM 读一遍，每读一个字节只做很少的计算，所以瓶颈在显存带宽。

Q5对 "aaabdaaabac" 用讲义的 BPE 做 2 次合并，结果是什么？

第 1 次：("a","a") 出现 4 次，最多，合并为 256 = "aa"，序列变成 aa a b d aa a b a c。

第 2 次：("aa","a") 和 ("a","b") 都出现 2 次，平局；("aa","a") 先出现，合并为 257 = "aaa"。

结果：aaa b d aaa b a c，11 字节 → 7 个 token。可以在上面的演练场里验证。

Q6为什么 encode 时必须按训练顺序应用合并规则？

后学到的规则可能由先学到的 token 组成（如 257 = 256 + "e"）。只有先应用前面的规则，后面规则需要的 pair 才会出现。按顺序应用，才能复现训练时的切分方式。

Q7词级 tokenizer 的 UNK 为什么会“搞乱困惑度”？

所有未登录词都被映射到同一个 UNK token。模型只需预测“这里是个生词”，而不必预测具体是哪个词，概率被人为抬高，困惑度显得更低。不同词表的模型 UNK 比例不同，困惑度也就没法公平比较。BPE 以字节为基础，任何文本都能表示，没有这个问题。

Q8为什么 GPT-5 tokenizer 会把 🌍 拆成两个 token？这对 decode 有什么影响？

BPE 在字节上合并，🌍 的 4 个 UTF-8 字节（F0 9F 8C 8D）在训练语料中不够常见，没有合并成一个完整 token。所以单个 token 的字节可能不是合法的 UTF-8。实现 decode 时要先把所有 token 的字节拼接起来再整体解码；逐 token 解码会出错，或者需要用 errors="replace" 处理不完整字节。
